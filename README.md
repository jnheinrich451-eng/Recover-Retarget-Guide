# Recover, Retarget, Guide

Camera and object motion transfer with a frozen video model: the code of the honours thesis (John Zeng, Australian National University, 2026; supervisor Dr Jing Zhang). This is the public copy of the method's repository: the source, the pipeline scripts and their configurations, the tests, the module contracts, the pipeline notebooks and the sealed records of the experiment. Probe scripts, caches, weights and videos are not included.

Given **one reference video** and **one text prompt**, the pipeline generates a new video whose camera and subject move like the
reference, in a scene the prompt describes. No target image is supplied: the target's first frame is synthesised. The video model
(Wan 2.1 I2V 14B) is used frozen; its weights, sampler and text guidance are unchanged.

```
reference video + prompt
   │
   ├─ Module 1  Recover    depth, camera path and subject path of the reference, lifted to one 3-D frame
   ├─ Module 2  Retarget   the target's first frame synthesised on the reference's layout; the subject reconstructed in 3-D and placed
   └─ Module 3  Guide      the recovered motion replayed in the target scene, rendered, and imposed on the frozen model at 16 of 50
                           sampling steps by a masked correction of the model's own prediction
```

The project page with the videos is https://jnheinrich451-eng.github.io/camera-object-motion-transfer/ (repository
`camera-object-motion-transfer`, generated by `scripts/make_project_page.py`). Figures and the measured tables are in [`results/`](results/). 

## Quick start: the bundled example

The clip `000000000265.2.005` (a man walking along a river, camera following) is the reference example of this repository, in two
retargetings: a red car on scrubland (`vehicle`) and a man on a rocky riverbank (`human`). Its intermediate caches (the Module 1 bundle,
the Module 2 anchor and handoff, the Module 3 geometry and renders) are published as a release asset so that Module 3 can be run on its own; the asset holds both pairs, `human` and `vehicle`.

1. Unpack the release asset `m3_example_265.2.005.zip` into a folder, say `DATA/`; it has the layout `DATA/cache/{m2_c,m2_d,m2_e,m3}/<clip>/<category>/`. The renders carry the targets the fixed configuration uses (`render_sky.npz` for the human pair, `render_obj_sky.npz` for the vehicle pair); `scripts/render_m3_target.py --sky-in-mask [--object]` rebuilds them from `lift.npz` and `geometry.npz` on a CPU.
2. Put the source clip at `DATA/videos/000000000265.2.005.mp4` (the DAVIS-style id is the file name).
3. On a GPU machine (A100 40 GB; L4 for the smoke test), install the Module 3 environment and run the sampler:

```bash
pip install -r requirements.txt -r requirements-phase2.txt
python scripts/run_m3_s4_guided.py --drive-root DATA --pair 000000000265.2.005/human --seed 0 --frames 33 --arm A0                          # no guidance
python scripts/run_m3_s4_guided.py --drive-root DATA --pair 000000000265.2.005/human --seed 0 --frames 33 --arm A3 --soft-mask --sky-mask   # ours
python scripts/measure_m3_a0.py    --drive-root DATA --videos-dir DATA/videos --pairs 000000000265.2.005/human --source-frames 33 \
       --videos A0_seed0_rec_F33.mp4 A3_seed0_rec_F33_sm_sky.mp4 source                                                                     # grade both against the reference
```

The videos land in `DATA/cache/m3/000000000265.2.005/human/`; the grader's table in `DATA/reports/m3_s4/a0_motion.md`. The whole batch
of the paper (six pairs, two seeds, both arms, grading, and an export of every video) is one driver:

```bash
python scripts/run_m3_batch.py phase1 --drive-root DATA     # CPU: geometry and renders (skipped when present and of record)
python scripts/run_m3_batch.py phase2 --drive-root DATA     # GPU: sampling
python scripts/run_m3_batch.py grade  --drive-root DATA     # GPU: CoTracker grader + mask-centroid arbiter
python scripts/run_m3_batch.py export --drive-root DATA     # every video + source + anchor + index.json, zipped
```

`--drive-root` is any folder with the `cache/` and `reports/` layout; on Colab it is the Google Drive folder the notebooks mount.

## Running the whole pipeline on a new clip

The three modules run in three environments and are never loaded together (Phase 1 preprocessing and Phase 2 generation are
memory-disjoint by rule). Each module is a runner over one clip; each writes to `cache/<stage>/<clip>/` and refuses to overwrite a cache
whose config hash matches. Thresholds live in `configs/calibration.lock.yaml` and are not edited by the code.

| step | runner | runtime | external models |
|---|---|---|---|
| Module 1: depth, tracks, camera, subject mask, dense subject tracks, heading | `scripts/run_pipeline.py --clip-id <clip>` (A → B → C → C.5 → B.5) | Colab GPU, `scripts/bootstrap.sh` | OpenD4RT, ViPE, SAM2 |
| Module 2: admission, proxy, placement and control, anchor, reconstruction and handoff | `scripts/run_m2a.py`, `run_m2b2.py`, `run_m2c_c3.py`, `run_m2d.py`, `run_m2e.py` (`run_m2a.py --clip-id <clip>`; the others `--clip <clip> --category vehicle|human`) | Colab GPU, `scripts/setup_sam3d.sh` for the reconstructor | FLUX.1 (T2I and Depth control), SAM 3D, Depth-Anything |
| Module 3: geometry, renders, guided sampling, grading | `scripts/run_m3_batch.py` (or the per-step scripts it calls) | Colab A100, `scripts/bootstrap_phase2.sh` | MoGe-2 (phase 1), Wan 2.1 I2V 14B (phase 2), CoTracker (grading) |

One command chains them for a clip, with done-checks per stage and the human review points Module 2 keeps (it stops there with
the command to run next, and resumes on the next call):

```bash
python scripts/run_all.py --env colab --clip 000000000265.2.005 --category human --module 1     # Module 1 (Phase-1 runtime)
python scripts/run_all.py --env colab --clip 000000000265.2.005 --category human --module 2     # Module 2 (stops at its reviews)
python scripts/run_all.py --env colab --clip 000000000265.2.005 --category human --module 3     # Module 3 (Phase-2 runtime)
python scripts/run_all.py --env local --clip 000000000265.2.005 --category human --status       # what exists, read-only
```

### The experiment set, with no human step

The 32 census passes (`configs/experiment_set.yaml`, frozen 2026-10-19) run under their own root (`colab_exp`) with the gates-only path:
the proxies of record are copied (never regenerated), the control review is its own gate record, the anchor is selected by the rule of
record (`scripts/select_m2d_anchors.py`), the prompt comes from the caption by a fixed rule (`src/anchor/m2d/auto_target.py`), and the
m2_e handoff verdict is the gate outcomes. A pair that fails a gate is a recorded outcome (`reports/experiment/run_all.json`) and the next
pair runs.

```bash
python scripts/run_all.py --env colab_exp --set configs/experiment_set.yaml --module 2 --auto --proxy-from /content/drive/MyDrive/motion_transfer
python scripts/run_all.py --env colab_exp --set configs/experiment_set.yaml --module 3 --auto      # Phase-2 session (configs/m3_batch_exp.yaml: 21 frames, seed 0)
python scripts/run_all.py --env colab_exp --set configs/experiment_set.yaml --status
python scripts/select_m2d_anchors.py select --pairs <all pairs>                                     # the set-level selection report (CPU, after Module 2)
```

`--env` picks a preset in `configs/environment.yaml`: the root that holds `cache/` and `reports/`, the folder that holds `videos/`, and the
interpreter per module step. On a local machine set `MT_ROOT` and `MT_DATA` in the shell (or edit the `local` preset); every runner takes
its paths from them, and paths are outside every config hash, so caches made on Colab stay valid locally. The module environments stay
separate: the Phase-2 requirements are never installed into the Phase-1 environment, and the reconstructor has its own.

A new clip goes through it with the configuration of record, and any change to its code
or configuration reopens it. The prompts of the six pairs of record are in `docs/m3_batch_prompts.json`.

## Running it yourself

**On Colab.** `colab_quickstart.ipynb` at the root of this repository is the entry point: it clones this repository (no token),
installs the Module 3 environment, downloads the release asset with the bundled example, takes the source clip from an upload
or from a path you give, runs the backbone and ours on one pair, and shows the videos. It needs an A100 (40 GB) runtime for the
sampler; Google Drive is optional (mount it to keep the outputs between sessions). The four notebooks under
`notebooks/development/` are the author's session records and are bound to the author's Drive; they are not entry points.

**On your own machine.** Set `MT_ROOT` to the folder that holds `cache/` and `reports/` and `MT_DATA` to the folder that holds
`videos/`; every runner reads them (`--drive-root` overrides `MT_ROOT`). Module 3 needs a GPU with 40 GB (Wan 2.1 I2V 14B in fp8;
bf16 needs 80 GB); Modules 1 and 2 run on 24 GB. Tokens: none for Module 3 (Wan 2.1 is public on Hugging Face); an `HF_TOKEN`
with access to FLUX.1-dev for Module 2; no GitHub token. The reference clips of the thesis are MiraData and DAVIS clips and are
not redistributed here; `scripts/bootstrap*.sh` try the author's dataset and continue without it (`SKIP_VIDEOS=1` skips the
attempt).

## Repository layout

```
configs/      stage_*.yaml, m3.yaml, m3_batch.yaml; calibration.lock.yaml (thresholds, human-owned)
src/          preprocess/ (Module 1), anchor/ (Module 2), generate/m3/ (Module 3)
scripts/      the pipeline runners (run_*.py), the Stage III checks the runners call (check_*.py), the page generator
docs/         prompts of the six pairs of record
tests/        contract and synthetic tests (no external model needed): python tests/<file>.py
results/      measured tables, figures, and links to the released videos
measurements/ the sealed records of the experiment and its instruments (json, md, csv); never videos or weights
```

Secrets are read from files outside the tree and never written into it; weights, videos and caches are never committed.
